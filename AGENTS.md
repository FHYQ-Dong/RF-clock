# AGENTS.md

Durable design constraints for the RF-clock RFSoC FPGA project.

The current design is in `plan/RF_clock_modules.md` (Chinese: `plan/RF_clock_modules_zh.md`). Two nodes exchange 5.8 GHz PRN bursts (two-way time transfer); the follower steers its FS725 so its 10 MHz and 1PPS follow the master.

## Architecture constraints

- **ARM does algorithms, PL does time and the per-burst measurement chain:** the PL keeps the raw tick, captures PPS and records timestamps; its slot engine starts every TX burst and RX window at its tick; it makes each burst from a chip stream (PRN, guard, measurement packet) through the RRC FIR, tracks the correlation peak in every RX window (peak, sub-sample position, carrier phase) and searches whole windows (see the next constraint), and assembles and decodes the measurement packets. The correlation reference is made from the same chips by the same RRC FIR, so it always equals what was transmitted. The ARM computes the chip sequences of fixed codes and the RRC coefficients and loads them into the PL, decides re-locks the PL leaves to it, runs acquisition on long windows in DDR, and runs TWTT, Kalman filtering and FS725 steering. Reason: the nodes exchange their measurements inside the bursts of a 2 ms ping-pong, not over a network, so each measurement must be ready and on air within 2 ms of the burst it measures, which the ARM cannot guarantee; making bursts from chips in the PL also lets keyed (encrypted) codes be generated per burst later. Other DSP still needs a measured reason to move into the PL.

- **Track every slot, search on demand:** the tracker correlates a few lags around the predicted peak in every window and is ready long before the node's next burst. A whole-window search, by parallel time-domain correlators in integer arithmetic (it matches the ARM's float64 correlation exactly; only the interpolation and the phase are rounded), starts only when the tracker has no lock (lost, or not yet found after start-up; then again on fresh windows until it locks) or the ARM asks; the ARM asks from time to time while locked, so that a lock on a wrong peak (a delayed copy, multipath) is found. One search runs at a time on a frozen copy of its window while the other window buffer keeps receiving; while it is busy, further requests are refused and counted. It reports, with the window's `PPS_COUNT`, slot and start tick: the strongest peak, the earliest peak within a set threshold of the strongest (the direct path arrives first; delayed copies and multipath arrive later), the peak-to-sidelobe ratio and the window status. The PL re-locks by itself only when the new peak lies within the tracker's range (about ±1 sample, the peak did not move); any other peak waits for the ARM, which checks the one-way delay first. Slots without lock carry invalid measurements; a search the ARM requests while locked does not invalidate the tracker's measurements. A peak outside the window's lag range is left to the ARM's long-window acquisition.

- **One coherent timebase per node:** RFDC sample clocks, the PL fabric clock and `raw_tick` are all derived from that node's FS725 10 MHz. Sample rates are integer multiples of the tick rate so sample index ↔ tick is exact. RFDC Multi-Tile Sync is required so datapath latency is identical across power-ups. With RFDC 2.6 on the RFSoC 4x2 this means: ADC and DAC tiles 0 and 2 both enabled, each on its own PLL, block 0 of every tile enabled. Tile 2 carries the signal; tile 0 exists to satisfy MTS, and since 2.1 DAC tile 0 also sends the output PPS (DAC_B) — do not remove it. Do not switch to on-chip clock distribution: a distributing DAC tile is limited to 7.0 GS/s.

- **Gap-free TX bursts from on-chip data:** a TX burst is made in the PL from on-chip data only (chip sequences and the assembled measurement packet through the RRC FIR, or a sample waveform preloaded into BRAM/URAM for tests) and played one beat per clock from its start tick to the end, with no gap or bubble. Active-burst backpressure is not a legal operating mode: if the DAC drops `tready`, enter `FAULT`; never pause and resume. Do not stream TX samples from DDR in the first version.

- **Lossless RX windows:** RX capture starts at its tick, is timestamped on the ADC side before any FIFO, and goes into the PL correlator's window buffer and, when the ARM asks for it (acquisition, verification), through an async FIFO and S2MM DMA to DDR. Windows need not be contiguous, but no beat may be lost inside a window, on either path. A FIFO overflow inside a window invalidates that window (one lost measurement), not the whole system: flag and count it, do not enter `FAULT`.

- **Timestamps are tick anchors:** each burst/window has one start tick; per-sample time is `start_tick` plus sample index / Fs. Do not attach per-sample timestamps. Sub-sample timing comes from the correlation of the window in the PL.

- **Calibrated constants are explicit:** non-reciprocity Δ, PPS sub-tick phase and RFDC latency are measured and stored with a version. Never subtract a guessed constant. θ₀, B's steering target (Δ/2 and the two PPS paths of the shared reference), depends on both boards and the wiring between them, so it lives in `links/<A's S/N>_<B's S/N>.json`, one entry per wiring, not in a board config or the package.

- **What belongs to one board lives in its board config:** `/etc/rf-clock/board.json` (`rf_clock.pl.board_config`, docs/ABI.md §11.1), named by the board's AT24MAC402 serial number; `PL.open()` refuses a config for another board. Each LMX2594's VCO band is forced from it, because the calibrated band can change at every clock write and move a converter by 8-10 ps, and MTS picks its SYSREF capture windows by the codes it records, because the window nearest code 64 can change by a whole sample. The FS725 that clocks the board is recorded there too, by its serial number, with the gain the link sets at its start and its frequency lock loop at that gain, which the predictive control law steers by: at the same gain, one unit's integrator is 1.7 times the other's; for the unit steered through FC (B's), also its crystal's answer to FC (`fs725.fc`). Never put one board's value in the package.

- **One register map:** `PL/src/p_regs.vh` (addresses, bit fields) and `PL/src/p_defs.vh` (states, result codes, flags) are the RTL source for the ARM-visible interface; `docs/ABI.md` documents it for software. RTL and testbenches use these names, never raw offsets. Any change updates all three and bumps `VERSION` per `docs/ABI.md` §14.

- **English documents are the reference:** each Chinese translation (`*_zh.md`) is updated in the same change; docstrings and code comments are English.

- **The overlay ships with the package:** `src/rf_clock/overlay/` holds `rf_clock.bit`/`.hwh` and `rf_clock_hw.xsa` (Git LFS) and `manifest.json`, copied from a build directory by `tools/package_overlay.py`. The package version is `A.B.C.D`: A.B equals the register map `VERSION`, C counts bitstreams built for it, D counts Python-only releases. The build script writes it into P2 `BUILD_VERSION`, and `PL.open()` refuses a bitstream whose A.B.C differs from the installed package. Bump C (reset D) before building a new bitstream, and A.B together with `VERSION`; Python-only changes bump D (`docs/ABI.md` §14.1).

## Documents

- **Mechanisms are explained as a complete chain:** a report's phenomenon and mechanism go from the cause to the measured quantity link by link, without skipping a step the reader needs to follow it (for example: VCO band → tuning voltage → LMX2594 output phase → tile sample clock against SYSREF → MTS capture codes and the loopback time). Each link starts from the previous link's effect as its cause ("that output moved, so the tile PLLs locked to it move the sample clocks …"), rather than listing facts side by side. Say which links were measured and which are inferred.
- **A verified finding is written in one order, so that it reads straight through:** the phenomenon; the background knowledge needed to follow it; the complete causal chain that produces it; the experiments that test that chain; their results.
- **Markdown is not hard-wrapped:** each paragraph and each list item is one line, broken only where it ends; the renderer wraps. Tables, code blocks and headings are written as usual.
- **Explain hardware with diagrams, not register names:** draw the clock tree or the signal/flow path as a block diagram wherever a mechanism runs through hardware, and use as few register and pin names as possible. Every register or pin name that does appear says which block or wire of the diagram it controls or connects (for example "SYNC_DISx: the switch in front of divider x's reset input"). A figure cited from a data sheet gives the document, page and title, and the part that matters is redrawn in the text.
- **Reports link the reports they mention:** every mention of another report, by name ("the LMX report") or by path, is a relative Markdown link to its `REPORT.md` (from a Chinese file, `REPORT_zh.md`) or, where it has none, its `README.md`. Data series without a report stay as code paths.
- **One term per concept, in every document and both languages:** a concept keeps one name, defined where it first matters, and synonyms are not mixed in. Current terms: capture code, with T1 / PLL capture code where the two differ (捕获码, T1 / PLL 捕获码), not delay tap, DTC code or T1 code; MTS offset, not marker offset; VCO band (VCO 档位), not capacitor band or 电容档; loopback delay (回环延时), not loopback time or 回环时间; acquisition code (引导码), the known code bursts use until acquisition is done, never 捕获码, which is the capture code; measurement packet (测量包), the data behind the PRN in a burst; slot (时隙), one 2 ms turn of the ping-pong, identified by `PPS_COUNT` and its slot number, not round, 轮次 or exchange number; output PPS (输出 PPS), the PPS edge the PL makes from its tick (plan/pps_output.md), not the FS725's 1PPS, which stays the node's PPS input; steering error (修正误差), θ − θ₀ while B is steered, the clocks' relative wander the loop has not yet taken out, not θ's wander (游走, the free-running clocks' movement about their drift line) nor θ's noise; frequency lock loop (FLL, 锁频环), the FS725's loop that holds its crystal to the rubidium transition (`docs/fs725_principles.md`), not its 1 pps phase lock (PL, 1 pps 锁相环); predictive control law (预测控制律), `rf_clock.twtt.steer.PredictiveSteering`, and Kalman control law (Kalman 控制律), `Steering`, the two ways of steering B's SF, not MPC or controller names mixed in; steering through FC (改写 FC 来修正), the predictive control law setting the crystal's tuning FC with B's unit at GA 1 (`--steer-actuator fc`), rather than SF through the FLL. A new term is added to this list when it is introduced.

## Review rule

Design advice must be checked against the constraints above. Suggestions that rely on active-burst backpressure, inserted bubbles, dropped beats inside an RX window treated as valid data, DDR-streamed TX in the first version, or clocks not derived from the node's FS725 are invalid for this project.

## Remote development and synchronization

- **Remote development machine:** RF-clock-PC, reached from the development machine as the ssh alias `RF-clock-PC-ai` (an SSH key for AI tools). Documents call it RF-clock-PC.
- **Vivado environment:** source `/tools/Xilinx/Vivado/2024.1/settings64.sh` before invoking Vivado on `RF-clock-PC`.
- **Syncthing:** except for Git metadata, Python caches, `.venv`, and similar excluded directories, the other source code and documentation are synchronized automatically with `~/Program/RF-clock` on `RF-clock-PC`.
- Do not assume that generated build products or excluded cache directories are synchronized; verify their location on the machine where they are needed.

## Version snapshots

- **Snapshot every finished version, when the next one begins:** whenever a change calls for a new package version (docs/ABI.md §14.1), and not only when a commit is asked for, run `pwsh tools/snapshot_version.ps1` in the background before the first edit for that change. The working tree then holds the finished version that `pyproject.toml` still names: the script checks it in a worktree of its own in a temporary directory (pytest, pyright), builds its wheel into `dist/` (not in Git) beside `dist/rf_clock-<version>.json` and the log, and keeps its tree as `refs/snapshots/<version>`. Then bump the version and make the change. A failed snapshot is fixed in that version before the next one starts.
- **Commits by version use the snapshots:** each version's commit is `git commit-tree -S -p <parent> -F <message> refs/snapshots/<version>`, in version order, so no intermediate state is rebuilt and no version is tested again at commit or release time; delete a snapshot ref (`git update-ref -d`) once its version is committed, and release a version from its wheel in `dist/`.
